# 사용자 행동으로 보는 전체 흐름

[← 학습 가이드 목차](./README.md) · [이전: 프로젝트를 5분 만에 이해하기](./00-project-in-5-minutes.md)

## 이 문서에서 답할 질문

> 사용자가 사이트에 접속하거나 기록을 조회·저장할 때 요청은 어떤 순서로 이동하는가?

앞 문서에서는 프로젝트의 구성 요소와 역할을 살펴봤다. 이제 같은 구성 요소가 실제 사용자 행동에
따라 어떤 순서로 움직이는지 살펴본다.

이 문서는 Next.js 프론트엔드와 Python API를 함께 실행하는 전체 애플리케이션을 기준으로 한다.
Python API 없이 프론트엔드만 실행할 때 사용하는 개발용 로컬 저장 방식은 개발 작업 방식 문서에서
별도로 다룬다.

## 흐름에 등장하는 다섯 부분

- **브라우저**: 사용자가 사이트를 보고 조작하는 프로그램
- **프론트엔드**: 브라우저에 화면을 표시하고 사용자 행동을 요청으로 만드는 코드
- **백엔드**: 요청, 사용자, 입력값을 확인하고 데이터 처리를 담당하는 Python API
- **Supabase Auth**: 회원가입과 로그인 사용자를 확인하는 서비스
- **PostgreSQL**: 회원·식단·체중 데이터를 영구적으로 보관하는 데이터베이스

사이트에 접속할 때는 도메인과 DNS도 등장한다. 접속이 끝난 뒤의 조회·저장 흐름에서는 위 다섯
부분을 중심으로 보면 된다.

## 먼저 보는 공통 왕복 구조

```text
사용자 행동
→ 브라우저의 프론트엔드
→ Vercel의 Python 백엔드 API
→ Supabase Auth·PostgreSQL
→ Python 백엔드 API
→ 프론트엔드 화면
```

요청은 오른쪽으로만 이동하지 않는다. 백엔드와 Supabase가 처리한 성공 또는 실패 결과가 같은 길을
반대로 돌아와야 사용자가 화면에서 결과를 확인할 수 있다.

## 흐름 1: 사이트에 접속한다

### 시작 행동

사용자가 브라우저 주소창에 이 프로젝트의 실제 사이트 주소를 입력한다.

```text
https://www.food-broccoli.shop
```

여기서는 주소의 각 부분을 아직 나누지 않고, 사용자가 사이트에 들어가기 위한 **입구**라고만
생각한다.

### 이동 순서

```text
1. 사용자가 브라우저에 사이트 주소를 입력한다.
2. 브라우저가 이 주소에 연결된 Vercel을 찾는다.
3. 브라우저가 Vercel에 첫 화면을 요청한다.
4. Vercel이 Next.js가 준비한 화면 파일을 보낸다.
5. 브라우저가 전달받은 파일로 첫 화면을 보여준다.
6. 화면 코드가 실행되면 앱이 로그인 상태 확인을 시작한다.
```

`www.food-broccoli.shop`의 DNS 설정은 가비아에서 관리한다. 이 설정에는 이 도메인이 Vercel을
가리킨다는 정보가 들어 있다. 브라우저는 이 정보를 이용해 실제 화면을 제공하는 Vercel로 요청을
보낸다. 가비아가 화면을 만들어 보내는 것은 아니며, Supabase도 이 단계에서는 아직 등장하지 않는다.

주소를 찾는 구체적인 방법과 `www`가 없는 주소의 이동 과정은
[인프라와 배포](./07-infrastructure-and-deployment.md)에서 나중에 확대한다.

### 관련 코드

- [`src/app/layout.tsx`](../../src/app/layout.tsx): 모든 페이지가 공유하는 가장 바깥 구조
- [`src/app/page.tsx`](../../src/app/page.tsx): 날짜별 체중·식단 화면
- [`src/app/globals.css`](../../src/app/globals.css): 전체 화면에 적용되는 스타일

## 흐름 2: 로그인 상태를 확인한다

페이지 코드가 브라우저에 도착했다고 해서 기록 화면을 바로 보여주지는 않는다. 먼저 현재 사용자가
로그인한 회원인지 확인한다. 이 확인 과정을 여기서는 **세션 확인**이라고 부른다.

### 이동 순서

```text
1. AuthGate가 GET /api/authentication?action=session을 요청한다.
2. 브라우저에 이 사이트의 로그인 쿠키가 있으면 요청에 자동으로 함께 담긴다.
3. Vercel의 Python 인증 API가 요청을 받는다.
4. Python API가 Supabase Auth에서 로그인 사용자를 확인한다.
5. Python API가 members 테이블에서 이 앱의 회원인지 확인한다.
6. 확인 결과가 프론트엔드의 AuthGate로 돌아온다.
```

여기서 쿠키는 브라우저가 로그인 정보를 다음 요청에도 함께 보내도록 돕는 저장 수단이다. 쿠키 안의
토큰과 JWT가 어떻게 다른지는 인증 문서에서 단계별로 다룬다.

### 성공과 실패

- 로그인한 회원이면 안전한 회원 정보가 돌아오고 `AuthGate`가 기록 화면을 보여준다.
- 확인할 로그인 정보가 없거나 유효하지 않으면 `401` 로그인 필요 응답이 돌아오고 로그인 화면을
  보여준다.
- 기존 로그인 확인에 실패했지만 갱신에 필요한 정보가 남아 있으면, 인증 API가 세션 갱신을 한 번
  시도한다.

### 관련 코드

- [`src/app/layout.tsx`](../../src/app/layout.tsx): 모든 화면을 `AuthGate`로 감싼다.
- [`src/components/AuthGate.tsx`](../../src/components/AuthGate.tsx): 세션 확인 결과에 따라 로그인 또는 기록 화면을 선택한다.
- [`api/authentication.py`](../../api/authentication.py): 세션 확인과 로그인 요청을 처리한다.
- [`api/lib/auth.py`](../../api/lib/auth.py): 로그인 정보와 `members` 회원을 확인한다.

## 흐름 3: 날짜별 기록을 조회한다

로그인 확인이 끝나면 프론트엔드는 선택된 날짜의 체중과 식단을 불러온다. 사용자가 다른 날짜를
선택할 때도 같은 흐름을 반복한다.

### 이동 순서

```text
1. 사용자가 날짜를 선택한다.
2. 프론트엔드가 GET /api/day?date=선택한 날짜를 요청한다.
3. fetchApi()가 같은 사이트의 로그인 쿠키를 요청에 포함한다.
4. Python day API가 날짜 형식과 로그인 회원을 확인한다.
5. 백엔드가 member_id와 날짜를 조건으로 meals와 weights를 조회한다.
6. 백엔드가 하루 기록을 공통 응답 형식에 담아 반환한다.
7. 프론트엔드가 체중과 아침·점심·저녁·간식을 화면에 표시한다.
```

`member_id`는 어느 회원의 기록인지 구분하는 값이다. 날짜만 사용하면 같은 날짜를 기록한 여러
회원의 데이터를 구분할 수 없으므로 회원과 날짜 조건이 모두 필요하다.

### 실패하면 어떻게 되는가

- 날짜 형식이 올바르지 않으면 입력값 오류를 반환한다.
- 로그인 회원을 확인할 수 없으면 로그인 필요 오류를 반환한다.
- 서버 또는 Supabase 처리에 문제가 생기면 내부 정보를 숨긴 공통 오류를 반환한다.
- 프론트엔드는 기능에 따라 오류 메시지 또는 안전한 빈 상태를 화면에 표시한다.

### 관련 코드

- [`src/app/page.tsx`](../../src/app/page.tsx): 날짜 변경과 하루 기록 요청을 시작한다.
- [`src/services/apiClient.ts`](../../src/services/apiClient.ts): API 요청과 공통 응답 처리를 담당한다.
- [`api/day.py`](../../api/day.py): 회원과 날짜에 맞는 식단·체중을 조회한다.

## 흐름 4: 체중이나 식단을 저장한다

### 체중 저장 순서

```text
1. 사용자가 체중을 입력하고 저장 버튼을 누른다.
2. 프론트엔드가 빈 값인지, 숫자인지, 0보다 큰지 먼저 확인한다.
3. 프론트엔드가 PUT /api/weight에 날짜와 체중을 보낸다.
4. Python weight API가 요청 형식과 값, 로그인 회원을 다시 확인한다.
5. 백엔드가 member_id와 날짜를 기준으로 weights에 추가하거나 수정한다.
6. 저장 결과가 프론트엔드로 돌아온다.
7. 프론트엔드가 저장 완료 또는 오류 메시지를 표시한다.
```

프론트엔드에서 검사했더라도 백엔드는 값을 다시 검사한다. 브라우저에서 들어온 요청은 사용자가
개발자 도구나 다른 프로그램으로 바꿔 보낼 수 있기 때문에 백엔드가 그대로 신뢰해서는 안 된다.

### 식단 저장에서 달라지는 부분

식단은 `PUT /api/meal`에 날짜, 끼니, 음식, 식단 분류를 보낸다. 백엔드는 로그인한 `member_id`,
날짜, 끼니를 기준으로 `meals`에 추가하거나 기존 기록을 수정한다. 나머지 왕복 순서는 체중 저장과
같다.

### 관련 코드

- [`src/app/page.tsx`](../../src/app/page.tsx): 체중·식단 저장 요청을 만든다.
- [`src/components/MealCard.tsx`](../../src/components/MealCard.tsx): 한 끼의 입력과 저장 상태를 보여준다.
- [`api/weight.py`](../../api/weight.py): 체중 요청을 검사하고 저장한다.
- [`api/meal.py`](../../api/meal.py): 식단 요청을 검사하고 저장한다.

## 성공과 실패는 같은 길로 돌아온다

```text
성공: Supabase 결과 → Python API 성공 응답 → 프론트엔드 화면 갱신
실패: 검증·인증·서버 오류 → Python API 오류 응답 → 프론트엔드 오류 또는 빈 상태 표시
```

이 프로젝트의 공통 응답에는 처리 결과가 들어가는 `data`와 오류가 들어가는 `error`가 있다. 성공한
응답은 `data`를 사용하고, 실패한 응답은 `error`를 사용한다. JSON 문법과 HTTP 상태 코드는 HTTP와
API 문서에서 자세히 다룬다.

## 이해 확인

다음 질문에 자신의 말로 답해 본다.

1. 도메인을 찾은 뒤 브라우저의 페이지 요청은 어디로 가는가?
2. 앱이 처음 열릴 때 기록 화면보다 먼저 확인하는 것은 무엇인가?
3. 날짜별 기록 조회에서 `member_id`와 날짜가 모두 필요한 이유는 무엇인가?
4. 프론트엔드가 검사한 입력값을 백엔드가 다시 검사하는 이유는 무엇인가?
5. 성공과 실패 결과는 어떤 경로로 사용자에게 돌아오는가?

# 1부. 기존 서비스 분석

## 1. 서비스 목적

매일 먹은 음식을 **한 줄로 기록하고, 그 기록이 쌓인 패턴을 눈으로 확인하는 것**이 목적이다.

핵심은 기록의 간편함이다. 한 끼를 남기는 데 필요한 입력은 음식 이름과 `클린식 / 자유식` 두 가지 분류뿐이며,
칼로리·영양소·목표 체중 같은 수치 입력은 요구하지 않는다.

**이 서비스가 하지 않는 것** — 범위를 좁히는 것이 곧 이 서비스의 성격이다.

| 하는 것                    | 하지 않는 것               |
| -------------------------- | -------------------------- |
| 끼니별 음식 이름 기록      | 칼로리·영양소 계산         |
| 클린식 / 자유식 2단계 분류 | 식단 점수화·등급 판정      |
| 날짜별 체중 기록           | 목표 체중 설정·달성률 추적 |
| 캘린더로 패턴 확인         | 건강 진단, 의학적 조언     |
| CSV로 과거 기록 가져오기   | 식단 추천, 레시피 제공     |

---

## 2. 타겟 사용자

> **복잡한 칼로리 계산보다, 매일 먹은 음식을 간단히 기록하고 자신의 식단 패턴을 확인하고 싶은 사용자.**

구체적으로는 다음 조건을 함께 만족하는 사람이다.

- 식단 관리를 **혼자** 한다. 코치·트레이너에게 공유하거나 검사받을 목적이 아니다.
- 기록에 쓸 수 있는 시간이 **끼니당 10초 내외**다. 음식명을 적고 버튼 하나를 누르는 것이 한계다.
- 알고 싶은 것은 "오늘 몇 kcal 먹었나"가 아니라 **"이번 주에 자유식이 며칠이었나"** 다.
- 이미 스프레드시트나 메모장에 식단을 적어 왔고, 그 기록을 버리고 싶지 않다. (→ CSV 가져오기 기능의 근거)

전문 영양 관리 서비스가 아니라 **개인 식단 기록 및 패턴 확인 서비스**로 범위를 제한한다.

## 3. 주요 페이지

| 경로        | 파일                        | 역할                                          | 로그인 필요 |
| ----------- | --------------------------- | --------------------------------------------- | ----------- |
| `/`         | `src/app/page.tsx`          | 오늘(또는 선택한 날짜)의 식단 4끼 + 체중 기록 | 필요        |
| `/calendar` | `src/app/calendar/page.tsx` | 월 단위 캘린더로 클린/자유 패턴과 체중 확인   | 필요        |
| `/import`   | `src/app/import/page.tsx`   | 기존 다이어트일지 CSV 업로드                  | 필요        |

세 페이지는 모두 `src/app/layout.tsx`의 `AuthGate`로 감싸여 있다. 로그인하지 않은 상태에서는 페이지 내용
대신 로그인/회원가입 카드가 표시되므로, 위 경로는 실질적으로 **로그인 이후에만 도달 가능한 화면**이다.

페이지 간 이동은 두 가지 경로로 나뉜다.

- **`TabNav`** (`오늘 기록` / `캘린더`) — 모든 헤더에 상시 노출되는 주 내비게이션
- **햄버거 메뉴** (`SiteMenuButton` → 사이드 패널) — `가져오기`와 `로그아웃` 등 사용 빈도가 낮은 항목

> 참고: `TabNav`에는 **"통계" 탭이 없다.** 통계 기능 자체가 아직 없기 때문이며, 이번 개선의 핵심 신규 작업이다.

## 4. 기존 기능

### 4.1 회원가입 · 로그인 (`AuthGate.tsx` + `api/authentication.py`)

이메일 인증을 거치는 멀티 유저 인증이 구현되어 있다. `api/authentication.py`가 처리하는 동작은 다음과 같다.

| 액션                  | 메서드 | 설명                         |
| --------------------- | ------ | ---------------------------- |
| `signup`              | POST   | 가입 신청 후 인증 메일 발송  |
| `verify_email`        | POST   | 메일의 코드로 가입 확정      |
| `resend_verification` | POST   | 인증 메일 재발송             |
| `login`               | POST   | 로그인 및 세션 쿠키 발급     |
| `logout`              | POST   | 세션 쿠키 삭제               |
| `session`             | GET    | 현재 로그인한 회원 정보 조회 |

세션은 **HTTP 쿠키**(`diet_access_token`, `diet_refresh_token`)로 유지된다. 브라우저의 JavaScript가 토큰을
직접 들고 있지 않고, 서버가 쿠키에서 읽어 Supabase에 검증을 위임하는 구조다(`api/lib/auth.py`).

### 4.2 식단 기록 (`MealCard.tsx` + `api/meal.py`)

하루를 `아침 / 점심 / 저녁 / 간식` 네 칸으로 나누고, 각 칸에 음식 이름과 `클린식 / 자유식`을 저장한다.

- 저장은 `PUT /api/meal` 하나로 처리하며, `(회원, 날짜, 끼니)` 조합에 대한 **upsert**다. 같은 칸을 다시
  저장하면 새 행이 쌓이지 않고 덮어쓴다.
- 음식을 비운 채 저장하면 **`공복` + 클린식**으로 자동 저장된다. 자유식을 선택해 둔 상태여도 클린식으로
  저장한다. (2026-08-20 확정 정책 — WORK_LIST 45번, `portfolio subject.md`의 입력 차단 요구와는 의도된 차이)
- 저장 후에도 입력칸이나 분류 버튼을 건드리면 `수정` 버튼을 누르지 않아도 수정 모드로 전환된다.
- 하루치 전체 삭제는 `DELETE /api/meal?date=...` (화면의 `식단 초기화` 버튼)로만 가능하다. **한 끼만 지우는
  기능은 없다.**

### 4.3 체중 기록 (`page.tsx` + `api/weight.py`)

날짜별로 체중 1건을 저장한다(`PUT /api/weight`). 저장하면 입력칸이 잠기고 `수정` 버튼으로 다시 연다.
0 이하나 숫자가 아닌 값은 클라이언트에서 걸러 낸다.

### 4.4 캘린더 (`CalendarView.tsx` + `api/calendar.py`)

월 단위로 각 날짜의 **식단 상태 한 가지**와 **체중**을 함께 보여 준다. 날짜 칸의 상태는 다음 규칙으로 결정된다.

```
그 날의 끼니 중 하나라도 자유식  → free  (빨강)
끼니가 있고 전부 클린식          → clean (초록)
저장된 끼니가 없음               → 표시 없음
```

날짜를 누르면 그 날의 상세 기록이 모달로 열린다.

### 4.5 CSV 가져오기 (`import/page.tsx` + `api/import_data.py`)

기존에 쓰던 다이어트일지 CSV를 올려 과거 기록을 한 번에 채운다. `spreadsheetImport.ts`가 브라우저에서 먼저
파싱해 미리보기와 오류 목록을 보여 준 뒤 서버로 보낸다.

- 열 위치가 고정된 특정 서식만 지원한다(`9시 - 11시`, `체중` 헤더로 서식을 검증).
- `결식`으로 표시된 칸은 건너뛰고, 음식과 분류가 맞지 않는 행은 오류로 표시한 뒤 제외한다.
- 미래 날짜는 가져오지 않는다.

### 4.6 아직 없는 기능

- **최근 7일 통계** — 클린/자유 비율, 기록률 등
- **차트** — 체중 추이, 식단 분포
- **주간 식단 요약** — 데이터 기반 자연어 요약

이 세 가지가 이번 개선 프로젝트의 핵심 신규 작업이다.

## 5. 데이터 구조

Supabase(PostgreSQL)에 테이블 3개를 둔다. 정의는 `supabase/migrations/`에 순서대로 남아 있다.

### `members` — 회원

| 컬럼                        | 타입          | 설명                                     |
| --------------------------- | ------------- | ---------------------------------------- |
| `id`                        | `uuid` PK     | `auth.users(id)` 참조. 삭제 시 연쇄 삭제 |
| `email`                     | `text` UNIQUE | 로그인 이메일                            |
| `display_name`              | `text`        | 표시 이름 (1~50자)                       |
| `created_at` / `updated_at` | `timestamptz` | 생성·수정 시각                           |

### `meals` — 끼니 기록

| 컬럼                        | 타입          | 설명                                                            |
| --------------------------- | ------------- | --------------------------------------------------------------- |
| `id`                        | `uuid` PK     | 자동 생성                                                       |
| `member_id`                 | `uuid` FK     | `members(id)`, 연쇄 삭제                                        |
| `date`                      | `date`        | 기록 날짜                                                       |
| `meal`                      | `text`        | `breakfast` / `lunch` / `dinner` / `snack` 중 하나 (CHECK 제약) |
| `food`                      | `text`        | 먹은 음식 (앱에서 최대 500자)                                   |
| `type`                      | `text`        | `clean` / `free` 중 하나 (CHECK 제약)                           |
| `created_at` / `updated_at` | `timestamptz` | 생성·수정 시각                                                  |

- UNIQUE `(member_id, date, meal)` — 한 회원의 하루 한 끼는 한 행. upsert의 충돌 기준 키다.
- INDEX `(member_id, date)` — 하루/한 달 조회용.

### `weights` — 체중 기록

| 컬럼                        | 타입           | 설명                       |
| --------------------------- | -------------- | -------------------------- |
| `member_id`                 | `uuid` FK      | `members(id)`, 연쇄 삭제   |
| `date`                      | `date`         | 기록 날짜                  |
| `weight`                    | `numeric(6,2)` | 0보다 커야 함 (CHECK 제약) |
| `created_at` / `updated_at` | `timestamptz`  | 생성·수정 시각             |

- UNIQUE `(member_id, date)` — 한 회원의 하루 체중은 한 행.

### 접근 제어

세 테이블 모두 **RLS(Row Level Security)를 켜 두고, `anon`·`authenticated` 역할의 권한을 회수**했다.
브라우저는 이 테이블에 직접 접근할 수 없고, 서버(Python Function)가 `service_role` 키로만 읽고 쓴다.
회원 분리는 DB 정책이 아니라 **서버 코드가 모든 질의에 `member_id` 조건을 붙이는 방식**으로 보장한다.

```
브라우저 ──쿠키──▶ Python Function ──service_role──▶ Supabase
                    (member_id 필터를 여기서 강제)
```

## 7. 배포 구조

### 구성

```
GitHub (jmkm0520-glitch/diet, main)
   │  push
   ▼
Vercel ── 빌드 ──┬─▶ Next.js 정적/서버 렌더링  (src/)
                 └─▶ Python Serverless Functions (api/*.py)
                          │
                          ▼
                    Supabase (PostgreSQL + Auth)
```

### 배포 방식

- **자동 배포** — `main` 브랜치에 push하면 Vercel이 감지해 프로덕션 빌드를 실행한다. 별도의 배포 명령이
  필요 없다.
- **빌드 설정** — `vercel.json`에 `framework: "nextjs"`, `buildCommand: "pnpm build"`만 지정했다. `api/`
  아래의 `.py` 파일은 Vercel이 자동으로 각각 하나의 Serverless Function으로 만든다.
- **도메인** — `food-broccoli.shop`, `www.food-broccoli.shop`이 최신 프로덕션 배포에 연결된다.

### 환경 변수

프로덕션에 두 개가 등록되어 있으며 둘 다 **Sensitive**로 표시되어 값을 다시 읽을 수 없다.

| 이름                        | 용도                                               |
| --------------------------- | -------------------------------------------------- |
| `SUPABASE_URL`              | Supabase 프로젝트 주소                             |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 전용 접근 키. 브라우저에 절대 노출되지 않는다 |

`NEXT_PUBLIC_` 접두사가 붙은 변수가 없다는 점이 중요하다. Supabase 키가 클라이언트 번들에 들어가지
않는다는 뜻이며, 모든 DB 접근이 서버를 거치도록 강제된다.

### API 경로

| 경로                  | 메서드      | 역할                                  |
| --------------------- | ----------- | ------------------------------------- |
| `/api/health`         | GET         | 상태 확인                             |
| `/api/authentication` | GET, POST   | 세션 조회 / 가입·인증·로그인·로그아웃 |
| `/api/day`            | GET, DELETE | 하루치 식단+체중 조회 / 삭제          |
| `/api/meal`           | PUT, DELETE | 한 끼 저장 / 하루치 식단 삭제         |
| `/api/weight`         | PUT         | 체중 저장                             |
| `/api/calendar`       | GET         | 한 달치 상태·체중 조회                |
| `/api/import_data`    | POST        | CSV 일괄 저장                         |

모든 응답은 `{ "data": ..., "error": ... }` 형태의 동일한 봉투(envelope)를 쓴다. 프론트의 `apiClient.ts`가
이 형식을 검사하고, 형식이 어긋나면 `INVALID_RESPONSE`로 처리한다.

```

- 해결:  (무엇을 바꿨나 + 커밋)
- 확인:  (고쳐진 걸 어떻게 증명했나)
```

## 2026-08-20 — 기준선 확정 이전 작업

> 아래 4건은 Before 기준선을 잡기 직전에 처리한 것이라 **Before/After 표에는 넣지 않는다.**
> 다만 원인 분석 과정 자체는 값이 있어 **Trouble Shooting 재료로만 사용**한다.

### 1. 새로고침하면 없던 "공복 / 자유식" 기록이 되살아남

- **증상**: 아침·점심 칸에 입력한 적 없는 `공복`이 자유식(빨강)으로 저장되어 있고, 새로고침할 때마다 다시 나타남.
- **원인**: `MealCard.saveMeal()`에 `foodInput.trim() || "공복"`이 있었다. 빈 칸으로 저장을 누르면 코드가 `공복`을
  대신 채워 **DB에 진짜 행을 만들었다.** 자동 생성이 아니라 한 번 저장된 실제 기록이라 계속 되살아난 것.
- **해결**: 빈 값 처리 정책을 `getMealSaveInput()`으로 분리. 최종 정책은 **빈 칸 = `공복` + 클린식 자동 저장**이며,
  자유식을 눌러 둔 상태여도 클린식으로 저장한다. (`공복`을 자유식으로 기록하는 조합 자체를 없앰) — `830e14e`
- **확인**: 배포된 프로덕션 JS 번들을 직접 내려받아 문자열을 검사했다. 빌드 성공 표시만 믿지 않고
  `공복` 자동 대체 코드가 실제로 사라졌는지 / 새 코드가 들어갔는지를 확인.
- **한 줄**: 화면에 보이는 증상("자동으로 생긴다")과 실제 원인("한 번 저장된 진짜 데이터")이 달랐던 사례.
  코드를 고치기 전에 **데이터가 어디서 왔는지부터 확인**해야 했다.

> 이 항목은 Before/After 표에 쓰기 좋다.
> Before: 빈 칸 저장 → 의미 불명의 `공복 / 자유식` 기록이 남음
> After: 빈 칸 저장 → `공복 / 클린식`으로 일관되게 저장, 수정 버튼 없이도 바로 수정 가능

### 2. 햄버거 메뉴 버튼이 스크롤을 따라다님 (5번째 시도에서 해결)

- **증상**: 스크롤해도 메뉴 버튼만 화면에 떠 있어 본문 위를 덮음.
- **원인**: 버튼이 `position: fixed`(뷰포트 고정)였다. 이전에 네 번의 수정 시도가 있었는데
  (`c5f41b0`, `720a087`, `7962ee3`, `cfffe4e`) 모두 **fixed를 유지한 채 좌표만 조정**하거나
  헤더를 `sticky`로 만들어 따라가게 하려는 방식이었다. 헤더 sticky는 부모 `.main`에 `overflow: hidden`이
  걸려 있어 애초에 동작하지 않았다.
- **해결**: 좌표를 고치는 대신 **버튼을 헤더 DOM 안으로 옮겼다.** 메뉴 상태를 React Context로 공유하고
  `SiteMenuButton`을 분리해 세 페이지 헤더가 `오늘 기록 / 캘린더` 탭 옆에 직접 렌더하도록 변경. — `42a576d`
- **확인**: 배포된 CSS를 내려받아 `.menuButton`에서 `position:fixed`가 사라지고
  `.headerActions` 플렉스 컨테이너가 생긴 것을 확인.
- **한 줄**: 같은 버그를 네 번 고치려다 실패한 이유는 **증상(좌표)을 고치고 원인(배치 방식)을 안 고쳐서**였다.
  좌표 조정에서 구조 변경으로 접근을 바꾸자 한 번에 끝났다.

> 곁가지로 배운 것: 버튼이 다른 컴포넌트 트리에서 렌더되면서 `ref`를 Context로 넘기니
> `react-hooks/refs` 린트에 걸렸다. 포커스 복원을 `ref` → `id` 조회 방식으로 바꿔 해결.

### 3. 달력 아이콘을 눌러도 달력이 안 뜸

- **증상**: 날짜 선택 타일을 클릭해도 아무 일도 일어나지 않음.
- **원인**: 그 타일은 버튼이 아니라 `<input type="date">`를 `opacity: 0`으로 아이콘 위에 덮어놓은 것이었다.
  **크롬은 날짜 입력창의 자체 달력 인디케이터를 눌렀을 때만 달력을 연다.** 그 인디케이터가 투명 처리로
  안 보이니 클릭이 날짜 텍스트 영역에 떨어져 포커스만 됐다.
- **해결**: 클릭 시 `HTMLInputElement.showPicker()`를 직접 호출. API가 없거나 브라우저가 거부하면
  기존 동작(포커스 후 직접 입력)이 남도록 `try/catch`. — `fc97009`
- **한 줄**: "커스텀 디자인을 위해 네이티브 컨트롤을 투명하게 덮는" 흔한 패턴의 부작용.
  보이는 것과 클릭 대상이 어긋나면 브라우저 기본 동작이 깨진다.

### 5. 통계 집계를 어디서 할 것인가 (설계 판단)

- **선택지**: ① PostgREST에 GROUP BY를 밀어 넣기 ② 행을 받아서 Python에서 세기 ③ 브라우저에서 세기
- **선택**: ②. 근거는 **데이터 크기**다. 7일 × 4끼 = 최대 28행이라 네트워크로 옮기는 비용이 무의미하다.
  대신 집계 규칙이 `build_stats()` 한 함수에 그대로 보이고, DB 없이 테스트할 수 있다.
  ③을 고르지 않은 이유는 같은 규칙을 화면마다 다시 구현하게 되기 때문이다.
- **되짚어 볼 지점**: 창이 90일로 늘면 최대 360행이다. 그때도 같은 판단이 유효한지는 다시 봐야 한다.
  (`MAX_DAYS = 90`으로 상한을 걸어 둔 이유)

### 6. "통계 실패가 서비스를 멈추면 안 된다"를 어떻게 구현했나

요구사항이 추상적이라 세 층으로 나눠 해석했다.

| 상황                              | 처리                         | 이유                                                                    |
| --------------------------------- | ---------------------------- | ----------------------------------------------------------------------- |
| 기록이 0건                        | 0으로 채운 **정상 200 응답** | 데이터 없음은 오류가 아니다. 화면은 Empty State를 보여주면 된다         |
| `type`이 `clean`/`free`가 아닌 행 | 그 행만 건너뛰고 계속        | 한 행 때문에 통계 전체가 사라지면 안 된다                               |
| DB 연결·설정 실패                 | 500 + 오류 봉투              | 정직하게 실패를 알린다. 통계 화면만 오류를 띄우고 다른 화면은 영향 없다 |

- **한 줄**: "실패하지 않게 한다"가 아니라 **"어떤 실패를 어디까지 삼킬지 정한다"**가 실제 설계였다.

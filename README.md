# 오늘도 가볍게

칼로리 계산 없이, 매일 먹은 음식을 한 줄로 기록하고 그 패턴을 확인하는 개인 식단 기록 서비스입니다.

**배포** https://www.food-broccoli.shop

---

## 프로젝트 소개

이미 운영 중이던 식단 기록 서비스를 직접 사용하면서 UX 문제를 찾아 개선하고, 쌓인 기록을 집계하는
통계 기능을 새로 붙인 프로젝트입니다.

기능을 처음부터 만드는 것이 아니라 **이미 동작하는 서비스를 관찰해 무엇이 부족한지 스스로 정의하는
것**이 출발점이었습니다.

## 서비스를 만든 이유

식단 기록 앱은 대부분 칼로리와 영양소를 요구합니다. 끼니마다 무게를 재고 성분을 찾아 넣어야 하니
며칠 만에 그만두게 됩니다.

이 서비스는 입력을 **음식 이름과 `클린식 / 자유식` 두 가지**로 줄였습니다. 한 끼를 남기는 데 10초면
충분하고, 대신 "이번 주에 자유식이 며칠이었나"를 볼 수 있습니다.

범위를 좁힌 것이 이 서비스의 성격입니다.

| 하는 것                    | 하지 않는 것               |
| -------------------------- | -------------------------- |
| 끼니별 음식 이름 기록      | 칼로리·영양소 계산         |
| 클린식 / 자유식 2단계 분류 | 식단 점수화·등급 판정      |
| 날짜별 체중 기록           | 목표 체중 설정·달성률 추적 |
| 통계와 캘린더로 패턴 확인  | 건강 진단, 의학적 조언     |
| CSV로 과거 기록 가져오기   | 식단 추천, 레시피 제공     |

## 타겟 사용자

> 복잡한 칼로리 계산보다, 매일 먹은 음식을 간단히 기록하고 자신의 식단 패턴을 확인하고 싶은 사용자

- 식단 관리를 혼자 한다. 코치에게 공유하거나 검사받을 목적이 아니다.
- 기록에 쓸 수 있는 시간이 끼니당 10초 내외다.
- 알고 싶은 것은 "오늘 몇 kcal 먹었나"가 아니라 "이번 주에 자유식이 며칠이었나"다.
- 이미 스프레드시트에 식단을 적어 왔고, 그 기록을 버리고 싶지 않다.

## 기존 서비스

개선을 시작하기 전(2026-08-20) 상태를 기준선으로 기록했습니다. 화면 캡쳐 11장과 함께
[`docs/portfolio service-review.md`](<./docs/portfolio service-review.md>)에 정리되어 있습니다.

그 시점에 있던 것과 없던 것:

- **있던 것** — 회원가입/로그인, 식단 기록, 체중 기록, 캘린더, CSV 가져오기
- **없던 것** — 통계, 차트, 주간 요약. 탭에 "통계" 자체가 없었습니다.

## 개선 목표

직접 사용하며 UX 문제 7건을 찾고, 세 가지 기준으로 우선순위를 매겼습니다.

1. **서비스 목적과의 거리** — 이 문제가 "식단 패턴 확인"을 직접 막는가
2. **마주치는 빈도** — 매일 겪는가, 어쩌다 한 번인가
3. **회복 가능성** — 사용자가 스스로 우회할 수 있는가

HIGH로 분류한 3건을 개선 대상으로 확정했습니다.

| 문제                                     | 왜 HIGH인가                                            |
| ---------------------------------------- | ------------------------------------------------------ |
| 통계·차트·주간 요약이 없다               | 서비스 목적이 "패턴 확인"인데 그 수단이 통째로 없다    |
| 캘린더가 미기록 끼니를 판정에서 제외한다 | 없는 기능보다 **틀린 정보**가 나쁘다                   |
| 회원가입 제목이 `첫 회원 만들기`         | 비용은 한 줄인데 신규 사용자가 가장 먼저 보는 화면이다 |

## 사용자 흐름

로그인 / 식단 기록 / 기록 확인 세 흐름의 다이어그램은
[`portfolio.md`](./portfolio.md) 6장에 있습니다. 요약하면 다음과 같습니다.

```
접속 → GET /api/authentication?action=session (쿠키로 세션 확인)
   ├─ 세션 없음 → 로그인 / 회원가입 → 이메일 인증
   └─ 세션 있음 → 오늘 기록
                    ├─ PUT /api/meal   (회원·날짜·끼니 upsert)
                    ├─ PUT /api/weight
                    ├─ 캘린더  → GET /api/calendar → 날짜 클릭 → GET /api/day
                    └─ 통계    → GET /api/stats
```

## 식단 통계

`GET /api/stats`가 최근 7일(Asia/Seoul 기준 오늘 포함)을 집계합니다.

```json
{
  "range": { "start": "2026-08-14", "end": "2026-08-20", "days": 7 },
  "total": 21,
  "clean": 16,
  "free": 5,
  "cleanRatio": 76,
  "recordedDays": 6,
  "daily": [{ "date": "2026-08-14", "clean": 2, "free": 1, "weight": 55.2 }],
  "topMeal": "dinner",
  "previous": { "total": 18, "clean": 10, "free": 8, "cleanRatio": 56 },
  "cleanRatioDelta": 20
}
```

화면은 집계 카드 4개, 도넛 차트(클린/자유 비율), 날짜별 누적 막대, 체중 꺾은선, 그리고 주간 요약을
보여줍니다.

**설계에서 정한 것**

- **집계 위치** — 7일이면 최대 28행이라 행을 받아 Python에서 셉니다. 규칙이 함수 하나에 드러나고 DB
  없이 테스트됩니다.
- **차트 라이브러리 없음** — 도넛 1개와 막대 7개를 그리려고 200KB를 넣지 않았습니다. SVG/CSS로 직접
  그려 번들 증가가 없고, `<canvas>`와 달리 화면 낭독기가 읽을 수 있습니다.
- **AI 요약 없음** — 요약 문장은 고정 템플릿입니다. 문장마다 테스트로 검증되고, 이 서비스가 하지 않기로
  한 "진단성 표현"이 섞일 여지가 없습니다.
- **기록하지 않은 날을 지우지 않음** — `daily`에 0인 날을 남깁니다. 빼버리면 차트에서 공백이 사라져
  기록률이 보이지 않습니다.

## 시스템 구조

```
GitHub (main)
   │ push
   ▼
Vercel ──┬─▶ Next.js App Router      (src/)
         └─▶ Python Functions        (api/*.py)
                    │
                    ▼
             Supabase (PostgreSQL + Auth)
```

브라우저는 데이터베이스에 직접 접근하지 않습니다. 모든 질의는 Python Function이 `service_role` 키로
수행하며, 이 키는 서버 환경변수로만 존재합니다. `NEXT_PUBLIC_` 접두사가 붙은 변수가 하나도 없어
클라이언트 번들에 키가 들어가지 않습니다.

## 데이터 구조

### `members`

| 컬럼           | 타입          | 설명                  |
| -------------- | ------------- | --------------------- |
| `id`           | `uuid` PK     | `auth.users(id)` 참조 |
| `email`        | `text` UNIQUE | 로그인 이메일         |
| `display_name` | `text`        | 표시 이름 (1~50자)    |

### `meals`

| 컬럼        | 타입      | 설명                                         |
| ----------- | --------- | -------------------------------------------- |
| `id`        | `uuid` PK | 자동 생성                                    |
| `member_id` | `uuid` FK | `members(id)`, 연쇄 삭제                     |
| `date`      | `date`    | 기록 날짜                                    |
| `meal`      | `text`    | `breakfast`/`lunch`/`dinner`/`snack` (CHECK) |
| `food`      | `text`    | 먹은 음식 (최대 500자)                       |
| `type`      | `text`    | `clean`/`free` (CHECK)                       |

UNIQUE `(member_id, date, meal)` — 한 회원의 하루 한 끼는 한 행. upsert의 충돌 기준입니다.

### `weights`

| 컬럼        | 타입           | 설명                     |
| ----------- | -------------- | ------------------------ |
| `member_id` | `uuid` FK      | `members(id)`, 연쇄 삭제 |
| `date`      | `date`         | 기록 날짜                |
| `weight`    | `numeric(6,2)` | 0보다 커야 함 (CHECK)    |

UNIQUE `(member_id, date)`.

### 사용자별 데이터 분리

세 테이블 모두 RLS를 켜고 `anon`·`authenticated` 역할의 권한을 회수했습니다. 브라우저는 이 테이블에
접근할 수 없습니다.

다만 **분리를 보장하는 것은 RLS 정책이 아니라 서버 코드**입니다. 정책을 두지 않는 대신, 모든 질의에
`member_id` 조건을 붙입니다. 접근 경로가 Python Function 하나뿐이기 때문에 성립하는 구조이며,
브라우저가 직접 DB에 붙는 설계였다면 정책이 반드시 필요합니다.

## Trouble Shooting

### 1. 새로고침하면 없던 기록이 되살아난다

**증상** 입력한 적 없는 `공복 / 자유식` 기록이 아침·점심에 있고, 새로고침할 때마다 다시 나타났습니다.

**원인** 자동 생성이 아니었습니다. `MealCard.saveMeal()`에 `foodInput.trim() || "공복"`이 있어서
빈 칸으로 저장을 누르면 코드가 `공복`을 채워 **DB에 진짜 행을 만들었습니다.** 한 번 저장된 실제
데이터였기 때문에 계속 되살아난 것입니다.

**해결** 빈 값 처리를 `getMealSaveInput()`으로 분리하고 정책을 확정했습니다. 빈 칸은 `공복 + 클린식`으로
저장하며, 자유식을 눌러 둔 상태여도 클린식으로 저장해 의미가 어긋나는 조합 자체를 없앴습니다.

**배운 것** 화면에 보이는 증상("자동으로 생긴다")과 실제 원인("한 번 저장된 데이터")이 달랐습니다.
코드를 고치기 전에 **데이터가 어디서 왔는지부터 확인**해야 했습니다. 검증도 빌드 성공 표시가 아니라
배포된 JS 번들을 직접 받아 문자열을 확인했습니다.

### 2. 같은 버그를 네 번 고치고도 실패했다

**증상** 햄버거 메뉴 버튼이 스크롤해도 화면에 붙어 본문 위를 덮었습니다.

**원인** 버튼이 `position: fixed`였습니다. 이전 수정 네 번(`c5f41b0`, `720a087`, `7962ee3`, `cfffe4e`)은
모두 fixed를 유지한 채 좌표만 조정하거나, 헤더를 `sticky`로 만들어 따라가게 하려 했습니다. 그런데
헤더의 부모 `.main`에 `overflow: hidden`이 걸려 있어 sticky가 애초에 동작하지 않았습니다.

**해결** 좌표를 고치는 대신 **버튼을 헤더 DOM 안으로 옮겼습니다.** 메뉴 상태를 React Context로 공유하고
버튼 컴포넌트를 분리해 세 페이지 헤더가 탭 옆에 직접 렌더하도록 했습니다.

**배운 것** 네 번 실패한 이유는 **증상(좌표)을 고치고 원인(배치 방식)을 안 고쳐서**였습니다. 커밋
히스토리가 그대로 증거로 남아 있습니다.

### 3. 달력 아이콘을 눌러도 달력이 열리지 않는다

**증상** 날짜 선택 타일을 클릭해도 아무 일도 일어나지 않았습니다.

**원인** 그 타일은 버튼이 아니라 `<input type="date">`를 `opacity: 0`으로 아이콘 위에 덮은 것이었습니다.
크롬은 **날짜 입력창의 자체 달력 인디케이터를 눌렀을 때만** 달력을 엽니다. 그 인디케이터가 투명 처리로
보이지 않으니 클릭이 날짜 텍스트 영역에 떨어져 포커스만 됐습니다.

**해결** 클릭 시 `HTMLInputElement.showPicker()`를 직접 호출하고, API가 없거나 브라우저가 거부하면
기존 동작이 남도록 `try/catch`로 감쌌습니다.

**배운 것** 커스텀 디자인을 위해 네이티브 컨트롤을 투명하게 덮는 흔한 패턴의 부작용입니다. 보이는 것과
클릭 대상이 어긋나면 브라우저 기본 동작이 깨집니다.

### 4. 넣었다가 되돌린 기능

잘못 저장한 한 끼만 지우는 삭제 버튼을 만들었다가(`0df358c`) 전부 되돌렸습니다(`bbbe427`). 카드에
버튼이 하나 더 붙는 것보다 `저장 → 수정` 두 상태를 유지하는 쪽이 낫다고 판단했고, 잘못 저장하는 빈도도
낮았습니다. **되돌린 이유를 남기지 않으면 나중에 같은 기능을 또 만들게 됩니다.**

수동 확인이 필요한 시나리오(회원가입, 사용자 A/B 데이터 분리, 390px 반응형, 배포 환경 전체 플로우)는
[`docs/manual-test-checklist.md`](./docs/manual-test-checklist.md)에 절차로 정리했으며,
**2026-08-20에 Test 1~11 전부 통과**를 확인했습니다.

## 실행 방법

필요한 도구: Node.js 20 이상, pnpm, `python3.12`, Vercel CLI.

```bash
pnpm install
```

```bash
pnpm dev:vercel
```

`pnpm dev:vercel`은 [`scripts/vercel-dev.sh`](./scripts/vercel-dev.sh)를 실행해 Vercel 프로젝트 연결,
Development 환경변수 내려받기, `python3.12` 기반 `.venv` 준비, 의존성 설치, `vercel dev` 실행까지
처리합니다. Python 버전은 [`.python-version`](./.python-version)에 `3.12`로 고정되어 있습니다.

Python API 없이 프론트엔드만 띄우려면:

```bash
pnpm dev
```

Vercel 연결 없이 실행하려면 `pnpm dev:vercel --local`을 사용하고, 환경변수는 직접 준비합니다.

- `pnpm build` / `pnpm start` — 프로덕션 빌드·실행
- `pnpm test` — 프론트엔드 단위 테스트
- `pnpm lint` / `pnpm typecheck` / `pnpm format:check`
- `pnpm security:check` — 결과물·로그·Git 이력의 서버 비밀키 노출 검사

## 향후 개선 사항

우선순위에서 MEDIUM·LOW로 분류해 이번에 다루지 않은 항목입니다.

- **끼니별 삭제** — 현재는 하루 전체 초기화만 가능합니다. 넣었다가 되돌린 이력이 있어, 다시 넣는다면
  카드 버튼이 아닌 다른 방식이어야 합니다.
- **CSV 서식 확장** — 지금은 열 위치가 고정된 특정 서식만 지원합니다.
- **가져오기 화면 안내 보강** — 파일 선택 전 화면이 대부분 비어 있습니다.
- **통계 기간 선택** — API는 이미 `?days=`로 최대 90일을 지원하지만 화면에는 7일만 노출합니다. 기간이
  길어지면 집계 위치(Python vs DB)를 다시 판단해야 합니다.
